# Out-of-Syllabus v0.3 玩法重构实施计划

本计划把 v0.3 的交付目标定为完整可玩的序章：开场机关、普通战斗、两场动作卡牌战、三周目协作、超纲能力与双结尾连成一条主线。第一批必须交付从新游戏走到首次战胜阴影敌人的完整体验，随后继续完成全章。开发进度按可玩的内容和验证证据计算。

计划日期为 2026-10-04，代码基线为 `4074de5ad9f12fa7fef1bf83f5356b90841a529b`，引擎沿用 Godot 4.7.2。本文是待实施方案；本轮只检查了文档与源码，没有执行游戏回归，也没有改动游戏代码。v0.2 旧报告不能充当 v0.3 验收结果。

参考材料为用户提供的 `E:/Out-of-Syllabus_v0.3_Gameplay_Rebuild.zip` 及补充文字。ZIP 的 SHA256 为 `0CA11FE10A9EDBBDB5107A6A7D3AF4CD59FF811EC41FB7601F9A0EBFE13828FE`。包内的 `CODEX_START_HERE.md` 是后续执行参考，不改变用户本轮“制定计划”的请求。下文标明的初始参数和关卡安排是本计划提出的实现选择，尚未经过试玩平衡。

## 交付范围

保留六个区域、三次循环、过去真实操作影响现在、知识适用边界、超纲后果、双结尾，以及已经建立的存档校验、备份链路、测试隔离和固定 tick 语义事件。地图继续使用可编辑 TileMapLayer，世界保持 640×360、32×32 地图格和约 32×48 角色；中文 UI 独立布局。

将玩家主流程改为“看见障碍 → 操作物体 → 看见结果 → 把同一动作用于战斗 → 遇到条件变化 → 与过去的自己合作”。笔记和证据成为可回看的后台支持；通过阅读表单、勾选条件完成论证的旧战斗不再承担 v0.3 主线。

本版内容预算为一个普通战斗样例、两场阴影战、一个局部同步回声装置、六张常规动作卡和一张未来卡。攻击、移动、防御、结束回合及必要的松开操作作为基础指令，避免把基本生存能力和解谜退路绑在抽牌运气上。序章不扩到第二章，不增加通用任务编辑器或通用战斗框架。

v0.2 的源码基线、Windows 包、历史报告和用户存档保留。v0.3 新开 `schema 4 / content version 3` 与 `user://v0.3/`；本版不迁移旧局中状态，也不把旧概念卡、旧胜利和旧回声转换为从未发生的新操作。

## 一条完整的三周目路线

| 阶段 | 玩家真正做什么 | 获得什么 | 世界怎样改变 |
| --- | --- | --- | --- |
| 第一轮开场 | 在教室把同一张纸展开或揉团，放入计时机关后释放 | 最初两张动作卡及一条简短观察 | 门的机械延时发生可见变化，能走出教室 |
| 第一轮走廊 | 与巡逻纸偶进行短普通战斗，实际攻击、防御和使用已学动作 | 认识敌方意图和行动结果 | 巡逻障碍消失，进入实验区域 |
| 第一轮实验室 | 操作不同质量配重与夹具，完成双锤看守 | 调高、齐放；战后得到固定 | 金属配重的到达时刻实际控制护盾，实验室核心区开放 |
| 第一轮收尾 | 操作 A 稳压工位，完成一个有即时收益的短装置过程 | 原始 A 操作片段 | 打开当前轮需要的装置盒，并封存真实片段 |
| 第二轮 | 利用固定和纸片处理新障碍；准备好后敲同步铃，让 A 回声协助当前玩家操作 B 安全锁 | 原始 B 操作片段、密封组件就绪 | 完成下一轮真空装置所需的真实设备状态；允许预览后封存 |
| 第三轮实验室 | 敲铃启动 A/B 回声，当前玩家操作 C，完成抽气与释放 | 真空下的观察、抽气动作 | 联合装置完成，通往第二场阴影战的路线开放 |
| 第三轮阴影战 | 对抗风箱纸偶，先利用空气中的纸片变化，再应对玻璃舱抽成真空 | 理解同一动作在不同介质下的边界 | 通过改变装置条件完成战斗，进入档案室 |
| 档案室至观测塔 | 选择已有规律的安全路线，或使用借来的轨迹走捷径并承担追逐 | 分别完成两个有效结尾 | 最终在观测塔提交后结算章节，重试和读档不重复处罚或奖励 |

这是推荐关卡顺序，不把“是否打开某个 UI”当作进度条件。提前探索、合法提前观察和不同战斗解法均由已发生的事件更新引导。第二轮必须有独立问题和即时收益，不能只是返回实验室等待录像。

## 先确定的玩法规则

### 开场纸片门

采用可重复使用的机械计时门。玩家的释放动作启动计时器，纸片实际到达传感器的时间决定机关输出。初始设计使用可见的机械阈值和延时齿轮：超过阈值时延长开门时间，让玩家从容通过。这里放大的是机关反馈和通行时间，落体求解结果保持真实。

参考包给出现有参数下展开和揉团的差异约为 0.18 秒；这只是现有配置的参考值。本计划建议先测试约 0.74 秒的传感阈值和约 3 秒的通行窗口，随后按实际轨迹、移动时间及碰撞范围调整。必须覆盖初始就选对、先选错、重复尝试、站位较远和只用键盘的情况。该机关不要求玩家在 0.18 秒内反应。

物体变形、共用慢放、落地停帧和机械锁扣反馈一起解释因果。完成测量并把结果近景展示给玩家后，自动记录一句观察。远处回声产生的结果保留未观察状态；预测永远不写成测量。

### 普通战斗与动作卡牌战

象征界承担探索和短普通战，阴影界由具体异常触发动作卡牌战。普通战斗只做满足样例所需的最小规则：双方状态、敌方下一动作、攻击、防御、环境技能和结束结算。防御减少实际伤害，环境技能改变实际局面，胜利解除世界障碍。两类战斗共用必要的角色状态和结算事件，各自保留规则。

阴影战采用三条站位通道、每回合 2 AP、首战固定手牌。初始仅提供已学的 3 至 4 张动作卡，章末最多六张常规卡和一张未来卡。鼠标和键盘均采用“选动作 → 选目标 → 预览 → 确认或取消”。必要装置动作保证可再次取得；结构合法但效果不好的动作允许执行，给出可见结果。

拟定统一的回合时序：规划期间装置时钟暂停；修改形状、高度和夹持状态即时写入权威状态并展示，释放指令设置为本轮待释放。结束回合时，待释放、轨迹事件、装置命中与敌方意图进入同一固定 tick 结算阶段，按显式优先级处理。界面明确显示“本轮释放”。尚在运动的物体保留剩余状态，不因进入下一回合重置。动画只播放已算出的结果，跳过动画也得到同一语义状态。

| 动作 | 拟定费用 | 必须产生的结果 | 必须保留的限制 |
| --- | --- | --- | --- |
| 揉团 | 1 AP | 改变同一纸片的形状、迎风面积及相关阻力参数 | 不改变质量；不能对金属使用；真空中不制造空气阻力优势 |
| 展开 | 1 AP | 恢复纸片形状，改变遮挡面积与空气中的下落 | 不生成新纸片；几何遮挡与落体速度分开计算 |
| 调高 | 1 AP | 改变夹具中物体的实际释放高度 | 只作用于可调且未释放的夹具，不把飞行中的物体瞬移 |
| 齐放 | 1 AP | 两个已准备夹具在同一 tick 释放 | 同时释放不保证同时落地，仍计算质量、形状、介质和高度 |
| 固定 | 1 AP | 使用现有夹具保持目标位置或支撑遮挡物 | 校验夹具和目标；提供明确松开入口，防止永久锁死 |
| 抽气 | 2 AP | 改变有电、密封玻璃舱内的介质 | 不影响舱外；漏气、断电或不存在设备时说明原因 |
| 借来的轨迹 | 2 AP 或探索中的一次明确使用 | 按所选模型输出短期轨迹和操作窗口 | 预览和取消不记违规；错误模型不自动换成正确模型 |

双锤看守的初始关卡方案是左右配重高度不同、护盾由真实到达时间差控制。解法一抬高较低夹具后齐放；解法二防御预告的锤击，让敌人击低较高支架，再齐放。初始可试 1 米与 2 米高度、10 毫秒传感容差，但这些数值必须由轨迹与关卡测试确认。两路必须在受到的伤害、资源消耗或装置状态上存在真实差异。

风箱纸偶先让展开纸片遮挡扫描，或揉团快速触发机关。第二阶段只把玻璃舱变成真空；纸片的几何大小依然存在，空气造成的落体时间差消失。确定提供的替代解法是固定纸片、调整释放高度，再让实际到达时刻进入机关窗口。卡牌不要求玩家手输平方根公式，夹具提供离散刻度与可试错的可视窗口。首轮参数必须证明至少一个合法高度能进入窗口，不能只在提示里说“换个策略”。

两场阴影战分别用有限状态枚举找到至少两条机制不同的完整胜利路线，并检验条件变化后原策略是否仍有效。枚举使用正式命令入口；不把两串卡名不同视作两种解法。

### 局部同步回声

装置由玩家准备好后敲铃启动，统一倒数 3、2、1。第一轮保存 A，第二轮回放 A 并录制 B，第三轮回放 A/B 并由当前玩家操作 C。录制片段初始目标为 6 至 10 秒，包含具体操作、仪表变化和结束条件；不强制站满固定 12 秒。片段的长度由真实成功操作决定。

保留完整原始事件和原时间戳。片段引用原循环、起止事件、锚点、相对 tick、命令和姿态采样。回放保存 `source_tick` 与 `replay_tick`，绝不重写旧事件发生时间。只有本轮真实玩家操作进入新的录制轨道。

装置事件只能由一个作用域执行。标记为该装置作用域的源事件始终由局部播放器消费，全局轨道只保留历史展示。执行时将相关历史角色的因果控制交给局部装置，全局系统不再为同一角色生成第二个可作用实体。全局游标继续按规则推进；被接管角色的全局因果操作要记录接管原因，不延后补发奖励。结束后按当前全局时刻恢复表现。关卡不得同时要求这些角色在装置外执行另一个关键操作。

同一设备时钟驱动 A、B、C、压力、密封、释放与判定。暂停、慢放和快进对所有参与者一致生效，快进仍逐 tick 检查离位、断电、提前松开及条件变化。每个角色只能占用一个工位。

失败只恢复本次尝试开始前的设备与玩家状态。已封存片段及哈希不变；新的尝试可以再次执行同一来源动作，奖励仍按来源去重。第一版不提供回到第一轮任意重录并自动修补后续历史的编辑器。

### 超纲能力与后果

安全路线依据已观察的固定周期或已有记录，通过较长但可靠的校准路径。未来路线在接受之后还需要玩家选择模型、预览并实际使用，揭示平时无法可靠确定的短窗口，让玩家亲手经过明显更短的闸门路径。两路使用同一物理世界；区别在可获得的信息和可选路径。

P4 必须记录能力使用前后的路线长度、等待次数或暴露风险，至少有一项可见优势得到实测。玩家先成功利用优势，然后收到灯光、脚步和朝向明确的监考者预警，进入短追逐。不得用相同的闸门时间和相同路线冒充未来能力的收益。

接受选择、实际使用、违规结算、追逐相位和最终提交分别持久化。检查点位于优势已经兑现、追逐尚未开始的位置；接触失败恢复该点，保留已经登记的使用与违规事件，重新开始追逐。拒绝路线也有完整结尾。错误模型保留反例或计算不足提示，不自动替玩家纠正。

## 最小共享契约

先定义实际需要的字段与结果，再让 UI 与测试围绕同一接口工作。延续 `GameSession.command` 作为唯一因果入口，拆出有独立职责的模块，不新增第二套可以直接改世界的入口。

| 契约 | 必须包含的语义 |
| --- | --- |
| `ExperimentSetup` | 稳定物体 ID、质量、形状、面积、阻力参数、介质、释放高度、初速度、设备和来源；边界及默认值由版本定义 |
| `SimulationTrace` | 配置哈希、模拟器版本、固定步长、轨迹采样、到达与碰撞事件、测量结果；动画、预览和判定共用 |
| `ObservationRecord` | 物理来源、原始条件与轨迹引用、完成状态、观察状态及观察来源；预测独立保存 |
| `ActionRequest` 和 `ActionResult` | 请求 ID、状态版本、操作者、动作、目标、参数；结果区分结构不合法、合法无效、预期效果和意外效果 |
| `CombatState` | 遭遇、回合、AP、角色、物体、手牌与牌堆、敌方意图、设备时钟、活动轨迹、随机种子及唯一结算状态 |
| `GoalDef` 和引导状态 | 前置条件、真实完成事件、目标对象、短目标、递进提示、检查点策略；闲置计时只计算可操作时间 |
| `EchoSegment` 和尝试状态 | 来源循环与事件、锚点、相对 tick、姿态、参与者占用、游标、尝试 ID、已执行来源和奖励去重记录 |
| 知识与卡牌访问 | 发现、理解、许可、模型适用性分开；动作卡的拥有、解锁与当前可用性单独验证 |

预览与提交共用纯求解函数。预览不能消耗 AP、推进随机数、写入历史或触发存档；提交检查预览所对应的状态版本，过期则重新计算并提示玩家。非法命令保持状态不变，重复请求至多提交一次。展示层还须按知识权限过滤预览：没有掌握模型时提供定性提示或“不足以可靠预测”，不能因为求解器算得出就泄露完整未来答案。

HUD 只常驻短目标和附近操作，回声提示在相关装置附近出现，笔记为次级入口，设置和保存进入 Esc 菜单。提示按“问题 → 相关物体与性质 → 具体操作”递进，初始可试 30、60、90 秒的无进展阈值；阅读、暂停和演出不计入卡住时间。卡牌焦点、取消返回及目标选择由同一输入流程覆盖键盘和鼠标。

历史、战斗、局部装置、观察和检查点在候选会话完整验证后才交换到活动会话。备份、临时文件和主文件均接受新版完整校验；未来版本明确拒绝，不能回退备份掩盖不兼容。

## 阶段与完成门槛

六个阶段组织为三批可运行交付。每阶段完成相关回归与本地提交；获得实施授权后按依赖持续推进，不把阶段结束变成重复确认点。遇到可玩性问题先修当前链路，再继续扩充内容。

| 阶段 | 实施内容和主要文件 | 完成证据 |
| --- | --- | --- |
| P0 基线与契约 | 保留 v0.2；修证据快照、交互半径与卡牌访问；建立新版运行目录和最小契约。涉及 `core/game_session.gd`、`core/model_battle.gd`、`core/runtime_paths.gd`、保存模块和工具脚本 | 三个已知漏洞的反例通过，非法命令无副作用，旧目录不被新版读写；确认新旧版本启动路径 |

第一批交付覆盖 P0 至 P2，产物必须是可从头玩到首次阴影战胜利的构建。第二批覆盖 P3 至 P4，产物必须是三周目双结尾的完整构建。第三批 P5 交付可供外部试玩的本地发行候选包和验收材料。这样每批都增加可玩的实质内容，首批架构和 UI 不脱离主线单独验收。

## 工作区与集成方式

后续实施阶段建议沿用三条分工，在 P0 契约通过后启动隔离工作区。本轮不启动并行代理或创建实施分支。

| 分工 | 独占范围 | 可并行的产出 | 集成条件 |
| --- | --- | --- | --- |
| 主线与核心 | `GameSession`、模拟器、ActionResolver、存档、回声状态及契约 | 权威状态、最小场景、可玩关卡和集成 | 共享核心只有一个写入者；接口变化带版本和迁移说明 |
| UI 与资产 | 新战斗视图、实验近景、提示、角色与设备表现 | 用固定展示数据制作可交互界面，验收主角、纸片门、双锤样板后扩展 | 视图发信号、读展示数据；不自行判胜；契约变更回到主线整合 |
| QA 与构建 | 新版测试、输入路线、导出及报告脚本 | 从反例和正式命令生成断言，准备自然输入与内容校验 | 不改核心来迎合测试；只有指定工作区运行 GUI 和 Forge |

每个工作区和每次运行使用独立 QA profile，设置、保存、日志和截图全部隔离。主线决定集成顺序和最终构建提交。UI 与 QA 可从 P1 的固定契约开始并行，不必等完整主线完成才发现问题。

性能工作随实测问题推进：HUD 按状态变化更新，下一历史事件用游标读取，轨迹按配置哈希及模拟器版本复用；非法操作不存档。先测保存边界与帧停顿，再决定是否需要后台写盘，避免在可玩链路完成前扩大架构改造。

美术随首次可玩链路推进。先完成一个主角、纸片与夹具、实验室局部、双锤战场的读图验收，再补纸偶、监考者和其他装置。使用 imagegen 生成候选样板、pixel-art 检查像素网格、调色板与透明边，并查看实际引擎截图。不能通过检查的源图留在源素材目录；运行时使用有标记的可编辑占位。最终试玩报告明确哪些资产仍为占位。

## 验证矩阵

测试先保留仍成立的业务不变量，再替换改变了玩法的旧断言。备份恢复、未来版本拒绝、来源去重、候选恢复、历史不可变及条件边界继续保留。固定 02:00、固定长持有、六张初始概念卡、手工读取勾选及旧出牌顺序的测试留在 v0.2 基线；v0.3 用局部同步、逐步解锁、观察状态和物理结算测试替代，不为凑旧通过数恢复旧流程。

| 测试方向 | 必测内容 | 证据形式 |
| --- | --- | --- |
| P0 回归 | 新证据恢复、存读恢复、距离边界、未拥有卡、重复请求及非法结算 | 测试名、提交、命令和非零失败退出码 |
| 物理与观察 | 质量不变、不同高度与初速度、空气与真空、同一来源去重、预测不成为测量、未展示结果不标已观察 | 配置、轨迹摘要、数值容差和失败反例 |
| 战斗 | 错目标、无 AP、合法无效、意图实际执行、防御实际减伤、两种胜法、无软锁、胜败撤退唯一结算 | 正式命令路径和有限状态搜索结果 |
| 预览 | 连续 100 次预览与取消不改状态或随机数；状态改变后的旧预览失效；预览与提交一致 | 前后状态摘要与结算事件 |
| 回声 | 零历史开局、局部准备时间、来源不可改、作用域去重、缺任意角色、离位、断电、提前松开、局部重试 | 来源哈希、角色占用、游标与设备结果 |
| 时间一致性 | 正常推进、快进、慢放、跳过演出、检查点恢复、存读恢复 | 同一输入的语义状态与事件序列；不比较渲染帧数 |
| 存档 | 嵌套畸形、未来 schema/content、写盘失败、损坏→备份恢复→保存→再次损坏恢复 | 模拟故障与真实文件系统故障分别记录 |
| 两个结尾 | 走路、交互、选卡、选择模型、亲手通过闸门、追逐重试、塔内提交 | 独立 EXE 输入轨迹及实际截图；禁止瞬移、直接写世界或直接结算 |
| 画面与输入 | 960×540、1280×720、1366×768、1920×1080；手牌、目标、敌方意图、中文对话；鼠标与改键后的纯键盘路线 | 实际引擎截图和焦点序列，核心战斗操作不依赖纵向滚动 |
| 性能与构建 | 冷启动导入、资源完整、独立 EXE；30 分钟虚拟档案大小与保存耗时；真实帧耗时 | 原始测量、场景和采样条件；截图、保存及快进的停顿单独标记 |

三种输入验证分开报告。白盒输入可读取语义目标用于功能覆盖；自然 UI 验证必须从当前焦点使用真实方向键、Tab、确认、取消和鼠标，不能靠 `grab_focus` 跳到目标；真人盲测不能提前解释正确卡序或要求先读 README。

真人试玩目标为五名未读文档的玩家，其中至少四人能完成首个小循环并解释一次“操作导致结果”。这是产品验收目标，尚无本轮数据，也不构成统计保证。记录第一次有效操作、第一次理解、第一次胜利、失败次数、提示层级、卡点原话、对真空和回声的解释、未来能力的收益与代价。真人未完成时继续完成工程验证，把构建标为待盲测，不宣称可玩性已通过。

系统缩放、其他硬件、真实断电与磁盘写满分别列项；未测就写未测，不由正常文件写入测试代替。

## 交付文件与完成定义

执行时在 `build/v0.3/windows/` 生成新版 Windows 包，在 `reports/v0.3/<run-id>/` 保存原始日志、截图、断言、性能数据和清单。每份报告绑定 Git 提交、工作区是否有修改、引擎完整版本、构建哈希、命令及退出码。

维护 `docs/V03_CONTRACTS.md`、`docs/V03_PROGRESS.md`、`docs/V03_VALIDATION.md`，并在对应阶段更新现有设计、架构与路线图。进度表只列已通过门槛、当前阻塞和下一项可玩交付；不按文件数量或空泛百分比汇报。自动化验收、视觉检查和真人判断各有独立状态。

完成定义是：从全新 v0.3 记录出发，依靠场景操作完成开场与普通战，使用至少两种有效策略完成动作卡牌战，三轮记录形成必要且可重试的 A/B/C 合作，未来能力有先收益后代价的完整体验，两条路线均能在独立 EXE 内到达各自结尾，核心存档与因果不变量通过新版验证。所有待测人工项目随包说明。

实施的第一条连续任务链为：复现并修复三个现有入口问题 → 统一实验配置与轨迹 → 完成纸片门 → 接巡逻纸偶 → 接双锤看守 → 做一次从新游戏开始的自然 UI 通关。该链路通过后立即推进局部回声、第二场战斗和双结尾。构建只在本地生成，不自动推送或公开发布。
